\heading{1. Solution architecture: what problem do we solve?}
Customers should not need to discover every return condition or complete a long series
of cards. ReturnFlow accepts a natural-language request, checks trusted order data,
then presents the applicable conditions \textbf{together}. Customers can confirm them
collectively or describe only exceptions. Cards remain an explicit fallback, not the
primary goal. The prototype creates simulated return requests, not real refunds.

\heading{2. Technical architecture: how the components connect}
One CPU-only Jetstream2 VM runs Docker Compose. The backend is a \textbf{modular
monolith}, not a collection of agents: a single FastAPI application owns workflow,
policy and transactions. The selected model-enabled topology has \textbf{four containers};
guided fallback uses three. This figure specifies the candidate deployment, not a
claim that all four services have passed current cloud acceptance.

\heading{One request, end to end}
\begin{enumerate}
\item The browser posts the message and active question ID. Nginx forwards it to
FastAPI over the private Compose network; the response returns on the same path.
\item FastAPI checks the fictional account's order ownership and trusted order facts.
If configured, one Ollama call interprets text; exact-evidence/type checks filter candidates.
\item Application code binds a collective declaration to the current item, question
and policy snapshot, checks exceptions and eligibility, and persists the result in
PostgreSQL. A final check and atomic creation prevent duplicate simulated returns.
\item Policy lookup retrieves clauses from the same versioned policy source and
returns citations. It explains the policy; it does not replace the eligibility engine.
\end{enumerate}

\heading{A brief user example: normal path and exception}
These are intended interactions of the local candidate, not a recorded cloud trial.
Assume a fictional customer's owned item has passed delivery, deadline, sale and
duplicate-return checks. The reason is optional.

\begin{tabularx}{\linewidth}{@{}p{.13\linewidth}>{\raggedright\arraybackslash}p{.32\linewidth}Y@{}}
\toprule\textbf{Stage} & \textbf{Customer / interface} & \textbf{System behavior} \\
\midrule
Request & ``The shirt is too loose. I want to return it.'' & Verify ownership; select
the order/item. Do not assume clean, undamaged or intact tags from a fit complaint. \\
Checklist & Show stains, garment damage, removed tags and damaged tags together.
Invite a collective answer or exceptions. & Bind the displayed list to this item,
case version, policy and question. Do not preselect an answer. \\
Normal path & ``None of those problems apply, and please submit my return.'' & In
the intended model path, interpret declaration and consent together; perform final
checks and create one simulated RMA. The explicit button supports the same action. \\
Exception path & ``The shirt is clean, but the tags were cut off. Can I return it?'' &
Cite the relevant condition/origin clauses; ask whether this was already true on
arrival or happened later. Do not repeat unrelated questions or invent an exception. \\
\bottomrule\end{tabularx}

\heading{CI, smoke and manual continuous delivery}
\begin{itemize}
\item \textbf{CI checks the candidate:} Python lint/types/tests, PostgreSQL migrations
and API flows, frontend tests/build, then Linux AMD64 API/frontend image builds.
Image smoke runs those exact images with an isolated database and a guided demo flow.
Passing this smoke does not establish real Qwen performance.
\item \textbf{CD prepares a deployable release:} approved triggers publish the tested
image pair to GHCR with a commit/digest manifest. A human promotes it; the VM does not
rebuild source. This is continuous delivery, not automatic continuous deployment.
\item \textbf{Deployment protects state:} stop writes, back up PostgreSQL, migrate,
switch the paired images, then verify readiness, version identity and policy lookup.
Real-model CPU qualification and application smoke are separate gates for LLM mode.
Rollback must preserve new records and a compatible schema, not delete volumes.
\end{itemize}

\heading{Practical limits and next steps}
One VM has no failover or zero-downtime upgrades. A monitoring dashboard, off-host
backup retention and a two-release rollback rehearsal remain open. Only synthetic
accounts and orders are supported; there are no real refunds or physical inspections.
Recheck public HTTPS after unshelving. Candidate source: \texttt{e835d76} plus local
changes, not yet a published release.
