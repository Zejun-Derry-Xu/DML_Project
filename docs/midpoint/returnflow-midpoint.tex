\sectiontitle{1}{Problem, users and midpoint scope}
Customers often describe a return incompletely: they mention fit, but omit the order,
item condition or tag status. A conventional form asks every question up front; an
unconstrained chatbot may invent missing facts or make inconsistent policy decisions.
ReturnFlow separates \textbf{collecting a customer's statements} from
\textbf{authorizing a simulated return}. It guides customers through only the missing
information, explains the applicable policy, and routes unresolved cases to a durable
simulated support ticket.

\subheading{What a user can do}
Choose a fictional account, describe an apparel return, select an owned order/item,
answer condition questions with cards or text, review the result, and explicitly confirm
an eligible simulated return. A separate policy-help panel answers general questions
without modifying the active return. A refreshed page can recover the case.

\subheading{Engineering priorities}
\begin{itemize}
\item \textbf{Reliable deployment first:} one small application stack, reproducible images,
bounded model resources, version identity, backups and visible failure states.
\item \textbf{A replaceable AI boundary:} Qwen extracts candidate facts; application code owns
account/order checks, missing-information handling, policy decisions and confirmation.
\item \textbf{Explicit uncertainty:} an omitted condition is not a negative answer, and a
model's valid JSON is not proof of a true statement.
\end{itemize}

\subheading{Process: build, use and monitor}
The midpoint focuses on a complete small user journey, not on adding agents or training
a model. Development uses synthetic policy cases and public-data adapters; automated
checks protect the application path. Operational metrics support inspection, while
automated alerts and a dashboard remain planned.

\subheading{Execution: questions are normal API responses}
The backend returns the next question and approved choices as part of its response.
The browser renders them. The customer's next button click or text message starts a
new request; the server does not keep a connection waiting for an answer.

\subheading{State: uncertainty and final actions are durable}
Known, false, missing and conflicting observations are not interchangeable. Case state
and active questions persist in PostgreSQL. Support tickets are internal records, not
notifications to a real agent. A simulated RMA requires an explicit confirmation and
a duplicate-return check; refreshing the browser must not create another one.

ReturnFlow uses a \textbf{modular monolith}: one FastAPI process with separate route,
workflow, extraction, policy and persistence modules. It avoids the network and
coordination overhead of multiple agent services. The target is a CPU-only Jetstream2
VM; no GPU is required for the installed guided prototype.

\subheading{Containers and communication}
The installed guided stack has \textbf{three containers}: frontend, API and database.
A qualified model deployment would add Ollama as a fourth service. The API addresses
PostgreSQL and Ollama by Compose service DNS; container \texttt{localhost} is not the
host or another container. The platform proxy terminates TLS and forwards HTTP to Nginx
on VM port 5173; this is not end-to-end TLS to the container. API port 8000 stays
loopback-only; database/model ports are not published. Qdrant is not required by the
installed lexical/extractive policy path.

\subheading{Configuration, persistence and restart behavior}
Deployment uses \codefile{compose.jetstream.yml}, private environment settings,
named data/model volumes, health checks and \texttt{restart: unless-stopped}.
The restart policy restarts an exited process; an unhealthy flag alone does not imply
automatic repair. CPU/memory caps limit contention. Only synthetic data are permitted:
the fictional-account selector is not production authentication.

\subheading{Version identity}
The API and frontend images carry the source commit. A release manifest binds their
digests, schema expectation and policy checksum. Readiness checks database tables and
columns as well as application identity. A responding model endpoint or a green
\texttt{/ready} is not evidence that real model inference is accurate or fast enough.

\sectiontitle{4}{Prototype interaction, API and core analytic}
\subheading{A representative customer interaction}
\begin{enumerate}
\item Choose a fictional account and enter: \emph{``The jacket is too small;
I would like to return it.''} The interface requests selection of an owned order/item.
\item The API checks trusted order data: delivery, the 30-day return window,
final-sale status and an existing return. A failed precheck produces a policy-based
explanation rather than unnecessary condition questions.
\item For an eligible order, collect the raw return reason and the missing resale
conditions: stains, garment damage, attached tags and intact tags. The installed
guided mode uses explicit choices; an enabled LLM may interpret natural language.
\item If a condition remains unknown, collect the remaining information and create
a persistent simulated support ticket. Otherwise evaluate the versioned policy and
show an eligibility result or refusal with relevant clauses.
\item Only an eligible case with explicit confirmation creates a simulated RMA.
Reopening the case returns its stored state. No money is transferred.
\end{enumerate}
The full sequence above is an \textbf{illustrative walkthrough}. On October 24, a separate
browser session verified the public HTTPS path through account selection, return text,
an owned-order card, reason entry and a condition question, plus cited policy lookup.
It did not submit an RMA. Earlier cloud acceptance separately tested ticket persistence
and cross-account denial.

\subheading{Core analytic: language, policy and retrieval have different jobs}
The semantic component extracts only customer-stated candidate facts with evidence.
It does not decide eligibility. The configured policy requires appropriate resale
conditions; wearing alone does not cause refusal. Customer-caused adverse conditions
can be ineligible; arrival issues, defects and uncertain responsibility require review.

The current apparel policy is \codefile{apparel-1.0.0.json}. It supplies decision
parameters and rendered explanation clauses from one versioned source. Policy help
uses lexical retrieval and extractive answers in the installed configuration. This is
not a claim that an LLM or vector search authorizes returns. A policy change still
needs tests and a release; a new kind of policy may require application changes.

\notice{\textbf{Model boundary.} Exact evidence checks and structured JSON prevent some
mechanical errors, not all semantic mistakes. Wrong-item references, unsupported values,
negation and instructions inside user text remain known risks. Qwen trials and harness
experiments are not formal qualification or a claim of production readiness.}

\sectiontitle{5}{Continuous delivery, testing and recovery}
\subheading{Build once; promote deliberately}
GitHub Actions checks Python lint/types/tests, runs database migrations against real
PostgreSQL, exercises API workflows, and lints/builds the frontend. It then builds
Linux AMD64 API/frontend images, starts those exact images with an isolated database,
and performs HTTP smoke. An approved release trigger publishes the \emph{same} tested
images to GHCR and uploads an operator bundle; there is no second build on the VM.

Main pushes and explicitly authorized candidate tags can publish. Ordinary experiment
pushes only validate. The manually published candidate \texttt{\DeployedCommit} passed
\href{https://github.com/Zejun-Derry-Xu/DML_Project/actions/runs/40016963668}{CI validation,
image publication and artifact upload}. The newer \texttt{\SourceCommit} snapshot also
passed \href{https://github.com/Zejun-Derry-Xu/DML_Project/actions/runs/40035335912}{CI};
that does not mean it was deployed. \textbf{This is continuous delivery with manual
promotion, not automatic continuous deployment.}

\subheading{What smoke tests establish}

\subheading{Manual deployment sequence}
\begin{enumerate}
\item Validate the release manifest and immutable image pair; acquire a deployment lock.
Pull images and check commit labels before switching the application.
\item Stop API/frontend writes, take a PostgreSQL dump and verify archive readability.
Apply additive migrations using the new image; preserve existing volumes and records.
\item Start the selected image pair without rebuilding. Check frontend/API commit,
schema expectation, policy checksum and read-only smoke; record success only afterward.
\end{enumerate}
Failures stop the process with stage-specific errors. Some failures leave the app
stopped or a pending pair running; the runbook describes inspection and recovery.
No automatic database overwrite or destructive downgrade is used as a repair shortcut.

\subheading{Persistent data makes rollback different from code checkout}
The cloud adoption included a database backup and restoration into a separate test
database, then additive migration from schema \texttt{0002} to \texttt{0004}, preserving
historical cases and the existing simulated return. Archive listing alone would not
prove recovery, so the distinct restore check matters.

A rollback checker and unit tests exist, but a \textbf{real two-release compatibility
rehearsal is pending}. The deployment script refuses an unapproved old image pair.
Rolling back code must retain new business records and a compatible expanded schema;
it must not mean deleting a volume or restoring an old dump over new data.

\notice{\textbf{Current governance gap.} CI reports pass/fail, but main has no enforced
required-check rule in the last repository inspection. Branch protection, formal version
releases/change notes and the actual rollback rehearsal are next delivery tasks.}

\subheading{Known deployment limitations}
\begin{itemize}
\item \textbf{Access:} public HTTPS interaction was verified on October 24. Its proxy
hostname embeds the VM's public IP; shelving stops access and unshelving may change
the URL. Plain IP/HTTP is not the supported interactive entry.
\item \textbf{Reliability:} one VM, no replicas or automatic failover; upgrades have
planned downtime. Local backups need off-host retention. Metrics are exposed but no
deployed monitoring/alerting platform is claimed.
\item \textbf{Security and scope:} fictional accounts and synthetic orders only.
No production identity provider, real refund integration or physical-condition inspection.
\item \textbf{Model operation:} CPU cold starts/timeouts and unsupported facts remain
risks. Model experimentation is paused in favor of delivery work; the normal guided
prototype is not presented as a qualified Qwen-powered production service.
\end{itemize}

\subheading{Finish the checkpoint without expanding the architecture}
\begin{enumerate}
\item Confirm the full team roster and recheck the HTTPS URL before class. Keep the VM
running for the agreed demonstration; update the report if its public IP changes.
\item Refresh deployment/diagram evidence against the exact selected release. Clearly
label installed, experimental and planned components; retain the guided/model distinction.
\item Add required CI checks for main, complete a disposable two-version rollback
exercise, and add versioned release notes. These strengthen delivery without new agents,
training, Kubernetes or automatic production promotion.
\end{enumerate}
