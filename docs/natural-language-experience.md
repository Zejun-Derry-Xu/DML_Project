# ReturnFlow：自然语言优先的收集体验

> 本文记录前一版合并追问实现。当前默认已升级为 `checklist`，请先看
> [条件一次告知与整体声明](checklist-experience.md)。下文的 conversational/individual 为历史对照，
> 不代表当前默认体验；历史验证数不代表最新候选通过。

日期：2026-10-24。范围：本地实现和验证，不代表已经部署到 Jetstream2。

## 要解决的问题

减少用户提供信息的动作，不减少后台政策检查。用户不需要知道内部字段或政策，
也不需要把每个条件分别点一次。完整描述可以跳过收集步骤，但不会跳过订单归属、
期限、商品状态检查和最终确认。当前服装政策仍是 `apparel-1.0.0`。

## 新体验

1. 开场提供中性提示：退什么、为什么、衣服及吊牌现状；不知道可以直说。
   不预填“全部良好”，也不把示例文字当用户事实。
2. 用户可自由输入多行文字。Enter 发送、Shift+Enter 换行；中文输入法选词不会误发送。
   请求失败时保留草稿，允许重试。
3. 选中本人订单和商品后，原始开场描述仍会回放到现有提取器，不要求用户重说原因。
   日期、送达状态、final sale、重复退货仍由现有订单预检查处理。
4. 模型可用时，将缺少的原因及相关服装状态组合成一条描述请求。衣服的污渍/损坏、
   吊牌的连接/完整状态分别存储，只是一起询问，不是一个共享布尔值。
5. 部分回答后，只追问仍缺的字段。明确不知道的字段不反复追问；收集其他信息后，
   如仍不足则记录模拟人工工单。矛盾单独确认；成因只在异常分支询问。
6. 卡片作为折叠的“Prefer quick answers?”备用入口。展开后显示精确的单项问题，
   一个 Yes/No 只回答该项，不会把整个组合问题都填成同一个答案。
7. 订单/商品消歧、最终提交仍直接展示选项。事实摘要用可读名称；政策引用保留在
   可展开区域，不把每轮对话挤满内部字段和条款。

## 安全及降级

- `guided` 或提取失败时，仍使用单项问题，前端展开选项并说明自然语言理解不可用。
  没有模型时不能假装已经理解整句话。原因问题仍沿用原有的原文记录降级。
- 对混合字段的组合问题，单独的 yes/no 不被扩展成多项事实，而是提示澄清或使用选项。
- 部分回答算进展，不消耗其他字段的失败次数。连续两次没有回答当前任何待收集项时，
  才把这一组记为未解决，避免无限循环；不能因次数用尽而批准。
- `false`、未知和缺失仍区分。上下文用于指代，不代替当前消息证据。
- 不改模型、权重、事实证据校验或政策资格标准，不增加用于写追问的模型调用。
- 模拟 RMA 仍需要当前有效确认卡片；聊天里的 yes 不会直接提交。旧卡片版本校验保留。

## 代码地图

- `app/services/apparel_questions.py`：确定性的缺项分组和追问文案。
- `app/services/apparel_service.py`：实际问题文本/目标组传给提取器、部分回答计数、问题保存恢复。
- `app/api/schemas.py`：`QuestionResponse.requested_fields`、`option_prompt`，均为向后兼容新增字段。
- `frontend/src/apparelExperience.ts`：卡片显示原则及单项按钮文案。
- `frontend/src/ApparelApp.tsx`：开场、多行输入、可选卡片、摘要和引用。
- `tests/integration/test_apparel_delivery.py`：HTTP 多轮、未知、失效卡片、降级和确认回归。
- `frontend/tests/apparelExperience.test.mjs`：默认折叠、降级展开、确认可见、单项按钮范围。

不增加数据库列或业务接口；组合问题的信息存入现有案件 JSON，绑定具体 question_id。
刷新会恢复同一个问题和收集范围。历史问题无此元数据时按原单字段处理。

## 如何比较或退回旧的逐项收集方式

新增配置 `COLLECTION_STYLE=conversational`（默认）或 `individual`。
两种方式使用同一模型、提取验证器和政策，适合做交互对照。
`individual` 仅退回逐项提问；不是完整前端版本回滚。

合并收集只在 `EXTRACTION_MODE=llm` 且提取器可用时启用。云端示例仍保持
`EXTRACTION_MODE=guided` 的安全默认值，本轮没有启用云端模型或重启服务。
未来云端升级需构建匹配 API/前端镜像，运行现有验收流程后再启用 LLM 模式；
不能仅改变配置就宣称新体验或真实模型已经验收。

## 验证及下一次真人试用

本轮 HTTP/浏览器交互使用可控的语义替身验证流程；不把替身当作 Qwen 实测。
没有启动本地 Docker、真实模型，也没有恢复或修改云端。验证命令：

```bash
.venv/bin/ruff check --no-cache .
.venv/bin/mypy --cache-dir=/private/tmp/returnflow-ux-mypy app
.venv/bin/python -m pytest -q -p no:cacheprovider
cd frontend
npm test
npm run lint
npm run build
```

下一轮使用相同任务对照 individual/conversational，参与者交叉体验，避免只熟悉第二版。
包含只说“太小了”、一次完整描述、部分回答、不知道、异常到货、模型不可用和发送失败。
记录实际自然语言发送次数、卡片点击次数、重复问题数、任务完成率、放弃率、满意度、
从开始到完成的时间（包含阅读/输入及模型等待），另记真实 tokens 和模型冷热延迟。
必须检查是否遗漏必要条件或错误批准，不能仅用少点几次证明更好。

目前没有真人研究或真实 Qwen 下的轮次/延迟结论，也不承诺所有案件两轮结束。
自然语言自动选择订单/商品、语音输入、原文自动总结未包含在本轮；有歧义仍由订单卡片确认。

本地验证结果：后端 362 项通过，前端交互规则 5 项通过；Ruff、mypy、前端 lint 和构建通过。
HTTP 测试使用 SQLite；本轮未重新进行 PostgreSQL 集成实测。现有 Starlette/httpx 弃用警告仍在。
浏览器在独立的本机临时 SQLite 和脚本化提取替身下验证了：订单选择、组合补问、
部分回答后只问吊牌、选项默认折叠、断线保留草稿、恢复重试、最终摘要及显式确认入口。
浏览器没有点击最终提交，临时预览不接触开发或云端数据库。这些结果不是模型质量或真人效率分数。
新增前端测试已接入 CI 配置；本地通过不等于新的 GitHub CI 已完成。
